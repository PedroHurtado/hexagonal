# Día 4 — Bloque 2: Adaptador de persistencia JPA

> *"The database is a detail."* — Robert C. Martin, *Clean Architecture* (2017)

---

## 1. El problema en una frase

Queremos guardar y recuperar `Pedido` en PostgreSQL usando Spring Data JPA,
**sin que el dominio sepa que existe JPA**: ni `@Entity`, ni `@Id`, ni
constructores vacíos, ni setters públicos para que Hibernate sea feliz.

---

## 2. Intención

El adaptador de persistencia implementa el puerto `PedidoRepository` y
contiene **tres piezas**:

| Pieza                         | Tipo                                   | Responsabilidad                              |
|-------------------------------|----------------------------------------|----------------------------------------------|
| `PedidoJpaEntity`, `LineaPedidoJpaEntity` | `@Entity`                  | Modelo de tablas (lo que quiere Hibernate)   |
| `PedidoJpaRepository`         | `interface extends JpaRepository`      | Acceso a datos generado por Spring Data      |
| `PedidoPersistenceMapper`     | clase sin estado                       | Traduce dominio ↔ JPA                        |
| `PedidoPersistenceAdapter`    | `implements PedidoRepository`          | Orquesta: mapea, guarda, mapea de vuelta     |

Todo vive en `com.curso.pedidos.infrastructure.adapter.out.persistence`.

---

## 3. Bad: anotar el dominio con JPA

La tentación es enorme: "ya tengo `Pedido`, le pongo `@Entity` y listo".

```java
package com.curso.pedidos.domain.model;

import jakarta.persistence.*;          // ❌ JPA dentro del dominio

@Entity
@Table(name = "pedidos")
public class Pedido {

    @Id
    private UUID id;                   // ❌ adiós a PedidoId (value object)

    private UUID clienteId;            // ❌ adiós a ClienteId

    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true,
               fetch = FetchType.LAZY)
    @JoinColumn(name = "pedido_id")
    private List<LineaPedido> lineas = new ArrayList<>();  // ❌ LineaPedido también @Entity

    @Enumerated(EnumType.STRING)
    private EstadoPedido estado;

    protected Pedido() { }             // ❌ constructor vacío exigido por JPA

    public void setEstado(EstadoPedido estado) {   // ❌ setter que salta invariantes
        this.estado = estado;
    }
    // ...
}
```

### ¿Qué duele?

- **Los value objects desaparecen** o se convierten en `@Embeddable` con
  constructores protegidos: el modelo se deforma para la herramienta.
- **Invariantes debilitadas**: constructor vacío + setters = cualquiera puede
  crear un `Pedido` inválido.
- **Lazy loading** dentro del dominio: un `pedido.total()` puede lanzar
  `LazyInitializationException` fuera de la transacción. Un método de
  negocio que falla por un motivo técnico.
- **El dominio depende de `jakarta.persistence`**: ya no se compila sin JPA y
  la regla de dependencia está rota.
- **Cambiar el esquema** (renombrar una columna, partir una tabla) obliga a
  tocar el dominio.

## 4. Good: dos modelos y un mapper

### 4.1 ¿Por qué dos modelos?

| Modelo de dominio (`Pedido`)              | Modelo de persistencia (`PedidoJpaEntity`) |
|-------------------------------------------|--------------------------------------------|
| Optimizado para **reglas de negocio**     | Optimizado para **tablas y Hibernate**     |
| Value objects (`PedidoId`, `Dinero`)      | Tipos primitivos (`UUID`, `BigDecimal`)    |
| Inmutable donde se puede, sin setters     | Constructor vacío, getters/setters         |
| Cambia cuando cambia el negocio           | Cambia cuando cambia el esquema            |
| Sin dependencias                          | Depende de `jakarta.persistence`           |

El precio: **un mapper** y algo de duplicación. El beneficio: cada modelo
cambia por su propia razón (SRP a nivel de capa).

> Alternativa pragmática (Hombergs la llama *"No Mapping"* / *"Two-Way
> Mapping"* en su libro): en dominios CRUD muy simples se puede usar un solo
> modelo. En este curso usamos **dos modelos** porque `Pedido` tiene
> invariantes reales.

### 4.2 Esquema (Flyway)

```sql
-- src/main/resources/db/migration/V1__pedidos.sql
CREATE TABLE pedidos (
    id          UUID         PRIMARY KEY,
    cliente_id  UUID         NOT NULL,
    estado      VARCHAR(20)  NOT NULL,
    moneda      CHAR(3)      NOT NULL,
    creado_en   TIMESTAMP    NOT NULL,
    version     BIGINT       NOT NULL
);

CREATE TABLE lineas_pedido (
    id               BIGSERIAL     PRIMARY KEY,
    pedido_id        UUID          NOT NULL REFERENCES pedidos(id),
    producto_sku     VARCHAR(50)   NOT NULL,
    cantidad         INT           NOT NULL,
    precio_unitario  NUMERIC(12,2) NOT NULL
);
```

> Trampa: `BIGSERIAL` es de PostgreSQL. H2 lo acepta en modo PostgreSQL
> (`jdbc:h2:mem:test;MODE=PostgreSQL`). Si no, usa
> `BIGINT GENERATED BY DEFAULT AS IDENTITY`, que entienden ambos.

### 4.3 Entidades JPA

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import jakarta.persistence.*;
import java.time.Instant;
import java.util.ArrayList;
import java.util.List;
import java.util.UUID;

@Entity
@Table(name = "pedidos")
class PedidoJpaEntity {

    @Id
    private UUID id;

    @Column(name = "cliente_id", nullable = false)
    private UUID clienteId;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private EstadoPedidoJpa estado;

    @Column(nullable = false, length = 3)
    private String moneda;

    @Column(name = "creado_en", nullable = false)
    private Instant creadoEn;

    @Version
    private Long version;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL,
               orphanRemoval = true, fetch = FetchType.EAGER)
    private List<LineaPedidoJpaEntity> lineas = new ArrayList<>();

    protected PedidoJpaEntity() { }   // JPA lo exige; aquí no molesta

    PedidoJpaEntity(UUID id, UUID clienteId, EstadoPedidoJpa estado,
                    String moneda, Instant creadoEn) {
        this.id = id;
        this.clienteId = clienteId;
        this.estado = estado;
        this.moneda = moneda;
        this.creadoEn = creadoEn;
    }

    void reemplazarLineas(List<LineaPedidoJpaEntity> nuevas) {
        lineas.clear();
        nuevas.forEach(l -> {
            l.asignarPedido(this);
            lineas.add(l);
        });
    }

    void actualizarEstado(EstadoPedidoJpa estado) { this.estado = estado; }

    UUID getId() { return id; }
    UUID getClienteId() { return clienteId; }
    EstadoPedidoJpa getEstado() { return estado; }
    String getMoneda() { return moneda; }
    Instant getCreadoEn() { return creadoEn; }
    Long getVersion() { return version; }
    List<LineaPedidoJpaEntity> getLineas() { return lineas; }
}
```

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(name = "lineas_pedido")
class LineaPedidoJpaEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "pedido_id")
    private PedidoJpaEntity pedido;

    @Column(name = "producto_sku", nullable = false, length = 50)
    private String productoSku;

    @Column(nullable = false)
    private int cantidad;

    @Column(name = "precio_unitario", nullable = false, precision = 12, scale = 2)
    private BigDecimal precioUnitario;

    protected LineaPedidoJpaEntity() { }

    LineaPedidoJpaEntity(String productoSku, int cantidad, BigDecimal precioUnitario) {
        this.productoSku = productoSku;
        this.cantidad = cantidad;
        this.precioUnitario = precioUnitario;
    }

    void asignarPedido(PedidoJpaEntity pedido) { this.pedido = pedido; }

    String getProductoSku() { return productoSku; }
    int getCantidad() { return cantidad; }
    BigDecimal getPrecioUnitario() { return precioUnitario; }
}
```

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

/** Enum propio de persistencia: renombrar EstadoPedido en el dominio no rompe la BBDD. */
enum EstadoPedidoJpa { BORRADOR, CONFIRMADO, PAGADO, ENVIADO, CANCELADO }
```

Observa:

- Las clases son **package-private**: nadie fuera del adaptador las ve. Es la
  forma más barata de encapsular.
- **`@Version`**: bloqueo optimista. Dos usuarios confirmando el mismo pedido
  a la vez → uno recibe `OptimisticLockingFailureException`. Lo profundizamos
  en el día 6.
- `FetchType.EAGER` en las líneas: el agregado se carga **entero** siempre.
  Un agregado es una unidad de consistencia; cargarlo a medias no tiene
  sentido.
- **Moneda a nivel de pedido**: decisión de diseño (todas las líneas de un
  pedido en la misma moneda). El mapper la reconstruye en cada `Dinero`.

### 4.4 Repositorio Spring Data

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;
import java.util.UUID;

interface PedidoJpaRepository extends JpaRepository<PedidoJpaEntity, UUID> {

    List<PedidoJpaEntity> findByClienteId(UUID clienteId);
}
```

Spring Data detecta repositorios package-private sin problema. Este
`JpaRepository` es un **detalle** del adaptador: **no** es el puerto.

### 4.5 Mapper dominio ↔ JPA

El dominio necesita una forma de **reconstituir** un `Pedido` ya existente
sin pasar por `crear(...)` (que generaría un id nuevo y estado `BORRADOR`) ni
por `anadirLinea(...)` (que fallaría en un pedido `CONFIRMADO`). Para eso el
agregado expone una factoría explícita:

```java
// En com.curso.pedidos.domain.model.Pedido
public static Pedido reconstituir(PedidoId id, ClienteId clienteId,
                                  List<LineaPedido> lineas, EstadoPedido estado,
                                  Instant creadoEn) {
    return new Pedido(id, clienteId, new ArrayList<>(lineas), estado, creadoEn);
}
```

> Trampa: usar reflexión o hacer públicos los setters "solo para el mapper".
> Una factoría `reconstituir` con nombre explícito deja claro que **no es**
> para crear pedidos nuevos.

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import com.curso.pedidos.domain.model.*;
import java.util.Currency;
import java.util.List;

class PedidoPersistenceMapper {

    PedidoJpaEntity aEntidad(Pedido pedido) {
        var entity = new PedidoJpaEntity(
                pedido.id().valor(),
                pedido.clienteId().valor(),
                EstadoPedidoJpa.valueOf(pedido.estado().name()),
                monedaDe(pedido),
                pedido.creadoEn());
        entity.reemplazarLineas(aEntidades(pedido.lineas()));
        return entity;
    }

    void actualizarEntidad(PedidoJpaEntity entity, Pedido pedido) {
        entity.actualizarEstado(EstadoPedidoJpa.valueOf(pedido.estado().name()));
        entity.reemplazarLineas(aEntidades(pedido.lineas()));
    }

    Pedido aDominio(PedidoJpaEntity e) {
        Currency moneda = Currency.getInstance(e.getMoneda());
        List<LineaPedido> lineas = e.getLineas().stream()
                .map(l -> new LineaPedido(
                        new ProductoId(l.getProductoSku()),
                        new Cantidad(l.getCantidad()),
                        new Dinero(l.getPrecioUnitario(), moneda)))
                .toList();
        return Pedido.reconstituir(
                new PedidoId(e.getId()),
                new ClienteId(e.getClienteId()),
                lineas,
                EstadoPedido.valueOf(e.getEstado().name()),
                e.getCreadoEn());
    }

    private List<LineaPedidoJpaEntity> aEntidades(List<LineaPedido> lineas) {
        return lineas.stream()
                .map(l -> new LineaPedidoJpaEntity(
                        l.productoId().sku(),
                        l.cantidad().valor(),
                        l.precioUnitario().importe()))
                .toList();
    }

    private String monedaDe(Pedido pedido) {
        return pedido.total().moneda().getCurrencyCode();
    }
}
```

> Asumimos accesores estilo record (`id()`, `valor()`, `sku()`, `importe()`)
> como en los días anteriores. `Pedido.total()` en un pedido vacío devuelve
> `Dinero` cero en la moneda por defecto del pedido.

**¿MapStruct?** Para mappers con muchos campos planos ahorra mucho código. Con
value objects anidados y factorías como `reconstituir`, el mapper a mano suele
ser igual de corto y más legible. Regla práctica: empieza a mano; pasa a
MapStruct cuando el mapper sea aburrido, no cuando sea interesante.

### 4.6 El adaptador

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import com.curso.pedidos.application.port.out.PedidoRepository;
import com.curso.pedidos.domain.model.Pedido;
import com.curso.pedidos.domain.model.PedidoId;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;
import java.util.Optional;

@Component
class PedidoPersistenceAdapter implements PedidoRepository {

    private final PedidoJpaRepository jpaRepository;
    private final PedidoPersistenceMapper mapper = new PedidoPersistenceMapper();

    PedidoPersistenceAdapter(PedidoJpaRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    @Override
    @Transactional
    public Pedido guardar(Pedido pedido) {
        PedidoJpaEntity entity = jpaRepository.findById(pedido.id().valor())
                .map(existente -> {
                    mapper.actualizarEntidad(existente, pedido);
                    return existente;
                })
                .orElseGet(() -> mapper.aEntidad(pedido));
        return mapper.aDominio(jpaRepository.save(entity));
    }

    @Override
    @Transactional(readOnly = true)
    public Optional<Pedido> buscarPorId(PedidoId id) {
        return jpaRepository.findById(id.valor()).map(mapper::aDominio);
    }
}
```

¿Por qué `findById` antes de `save`? Porque nuestro id lo asigna el dominio
(UUID), no la base de datos. Si hiciéramos `save(new PedidoJpaEntity(...))`
con un id existente, Spring Data haría `merge` de una entidad **sin
`version`**, lo que con `@Version` provoca errores o pisa cambios. Cargar y
actualizar respeta el bloqueo optimista.

> **¿Y `@Transactional`?** En el adaptador marca la frontera de la operación
> de persistencia. La transacción **del caso de uso completo** (cargar →
> confirmar → guardar) es otra decisión que veremos en el día 6. Avance: se
> puede envolver el caso de uso con un decorador transaccional en
> `infrastructure.config` sin anotar la capa de aplicación.

## 6. Variantes y trampas

- **Trampa: devolver `PedidoJpaEntity` desde el puerto.** Si el caso de uso ve
  una entidad JPA, el adaptador no está adaptando nada.
- **Trampa: `PedidoRepository extends JpaRepository<...>`.** Es el error más
  frecuente en proyectos "hexagonales" con Spring. El puerto pasa a heredar 20
  métodos técnicos (`flush`, `saveAllAndFlush`, `findAll(Example)`…) y el
  dominio depende de Spring Data.
- **Trampa: un repositorio por entidad interna.** `LineaPedidoJpaRepository`
  no debería existir: las líneas se guardan con el agregado (`cascade`).
- **Trampa: consultas de lectura complejas por el repositorio del agregado.**
  Para listados/informes se puede definir un puerto de **consulta** separado
  (`ConsultarPedidosPort`) con proyecciones: es CQRS ligero (día 6/7).
- **Variante: JDBC.** Con `JdbcClient` (Spring 6.1) el adaptador implementa el
  mismo puerto sin JPA. Lo harás en el ejercicio del
  [bloque 7](07-ejercicios-dia-04.md).
- **Variante: Spring Data JDBC.** Encaja muy bien con agregados DDD (carga y
  guarda el agregado entero, sin lazy loading), pero sigue pidiendo
  anotaciones: mantenemos el modelo separado igualmente.

## 7. Testing: `@DataJpaTest` del adaptador

Lo que queremos verificar:

1. El mapeo **ida y vuelta** no pierde información (round-trip).
2. Actualizar un pedido existente reemplaza líneas y estado.
3. Buscar un id inexistente devuelve `Optional.empty()`.

`@DataJpaTest` arranca **solo** la capa JPA (entidades, repositorios Spring
Data, `DataSource` embebido H2, Flyway si está en el classpath). Nuestro
adaptador es un `@Component`, así que hay que importarlo explícitamente.

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

```java
package com.curso.pedidos.infrastructure.adapter.out.persistence;

import com.curso.pedidos.domain.model.*;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.context.annotation.Import;

import java.math.BigDecimal;
import java.util.Currency;
import java.util.UUID;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest(properties = "spring.datasource.url=jdbc:h2:mem:pedidos;MODE=PostgreSQL")
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import(PedidoPersistenceAdapter.class)
class PedidoPersistenceAdapterTest {

    private static final Currency EUR = Currency.getInstance("EUR");

    @Autowired PedidoPersistenceAdapter adapter;
    @Autowired PedidoJpaRepository jpaRepository;

    @Test
    void guarda_y_recupera_un_pedido_completo() {
        Pedido pedido = Pedido.crear(new ClienteId(UUID.randomUUID()));
        pedido.anadirLinea(new ProductoId("SKU-1"), new Cantidad(2),
                new Dinero(new BigDecimal("10.00"), EUR));
        pedido.anadirLinea(new ProductoId("SKU-2"), new Cantidad(1),
                new Dinero(new BigDecimal("5.50"), EUR));

        adapter.guardar(pedido);

        Pedido recuperado = adapter.buscarPorId(pedido.id()).orElseThrow();
        assertThat(recuperado.id()).isEqualTo(pedido.id());
        assertThat(recuperado.estado()).isEqualTo(EstadoPedido.BORRADOR);
        assertThat(recuperado.lineas()).hasSize(2);
        assertThat(recuperado.total())
                .isEqualTo(new Dinero(new BigDecimal("25.50"), EUR));
    }

    @Test
    void actualiza_el_estado_de_un_pedido_existente() {
        Pedido pedido = Pedido.crear(new ClienteId(UUID.randomUUID()));
        pedido.anadirLinea(new ProductoId("SKU-1"), new Cantidad(1),
                new Dinero(new BigDecimal("9.99"), EUR));
        adapter.guardar(pedido);

        Pedido cargado = adapter.buscarPorId(pedido.id()).orElseThrow();
        cargado.confirmar();
        adapter.guardar(cargado);

        assertThat(adapter.buscarPorId(pedido.id()))
                .get().extracting(Pedido::estado)
                .isEqualTo(EstadoPedido.CONFIRMADO);
        assertThat(jpaRepository.count()).isEqualTo(1);
    }

    @Test
    void devuelve_vacio_si_no_existe() {
        assertThat(adapter.buscarPorId(new PedidoId(UUID.randomUUID()))).isEmpty();
    }
}
```

Notas:

- **Comparación de `BigDecimal`**: `new BigDecimal("25.50")` vs lo que vuelve
  de la BBDD con `scale = 2` → iguales. Si tu `Dinero` compara con `equals`
  de `BigDecimal`, cuidado con las escalas (`10.0` ≠ `10.00`). Normaliza la
  escala en el constructor compacto del record.
- **`replace = NONE`**: por defecto `@DataJpaTest` sustituye el `DataSource`
  por una BBDD embebida generada e **ignora** `spring.datasource.url`. Como
  queremos H2 en modo PostgreSQL (para que Flyway acepte `BIGSERIAL`), le
  decimos que no reemplace nada y use nuestra URL.
- `@DataJpaTest` es **transaccional** y hace rollback al final de cada test:
  no hace falta limpiar.
- Para la primera lectura tras guardar, Hibernate puede devolver la entidad de
  la caché de primer nivel. Si quieres forzar ida real a la BBDD, inyecta
  `TestEntityManager` y llama a `flush()` + `clear()` antes de leer.
- **H2 vs PostgreSQL**: H2 es rápido para la demo, pero no es PostgreSQL. En
  el día 5 cambiamos a **Testcontainers** con
  `@AutoConfigureTestDatabase(replace = NONE)` y un `PostgreSQLContainer`.

Test unitario del **mapper** (sin Spring, milisegundos):

```java
class PedidoPersistenceMapperTest {
```

## 8. Resumen

| Decisión                              | Por qué                                            |
|---------------------------------------|----------------------------------------------------|
| Modelo JPA separado del dominio       | El dominio no se deforma por Hibernate             |
| Clases package-private                | Nadie fuera del adaptador ve JPA                   |
| `Pedido.reconstituir(...)`            | Rehidratar sin saltarse ni romper invariantes      |
| `@Version`                            | Bloqueo optimista en el agregado                   |
| Cargar-y-actualizar en `guardar`      | Ids asignados por el dominio + versión correcta    |
| `@DataJpaTest` + `@Import(adapter)`   | Test del adaptador aislado, contra BBDD real/embebida |
